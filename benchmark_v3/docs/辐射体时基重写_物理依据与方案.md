# 辐射体时基重写：物理依据与实施方案（v1 草案）

状态：**待用户确认后实施**。纪律：每个数字必须有可指名的依据；拿不到硬依据的一律标注
「待核对」，不自行编造。本文只改**源的时基**（事件率/驻留/周期），不改波形调制、不改窗长上限、
不改评测口径。

---

## 0. 为什么要改

现有生成器的时基是"按窗内样点数凑事件数"，不是物理速率。实测（`benchmark_v3/evidence/_emitter_timebase.txt`）：

| 类 | 物理事实 | 现在实测 | 差距 |
|---|---|---|---|
| Bluetooth_FHSS | **1600 跳/s，驻留 625 µs** | **61 k 跳/s**（609 跳/10 ms），驻留 **6–15 µs**（`dwell=(25,60)` 是样点） | 快 ~38×，驻留短 ~60× |
| Zigbee / WiFi_burst | 事件率由业务决定 | 突发段数**写死不随窗长变**（7 / 81），duty 按 1/窗长塌 | 长窗无意义 |
| DECT | **帧长 10 ms（100 帧/s）、24 时隙** | 3 帧/10 ms、duty 57% | 帧率 3×、duty 高一个量级 |
| Welder | 电弧重燃**100 Hz**（工频半周期）为主，逆变焊机另有 20–100 kHz | 583 突发/10 ms（≈58 kHz） | 主周期错 |
| Corona | 电晕脉冲**成组**出现在工频半周期（100/120 Hz） | 94 突发/10 ms | 主周期错 |
| Microwave（微波炉） | 磁控管半波倍压 ⇒ 泄漏按 **50/60 Hz** 调幅 | 2133 突发/10 ms（≈213 kHz） | 主周期错 |
| VFD_noise | PWM 载频 **2–16 kHz** | 646 突发/10 ms（≈65 kHz） | 载频高 |

结论：**当前时基下，拉长窗只会把错误时基放大**（Zigbee/WiFi 反而稀释 100 倍）。
所以"长窗题"和"时域题轴"都必须建立在真实时基之上。

1. Bluetooth：**已钉死** —— Core Spec v5.4 Baseband Specification 原文摘句（1600 hops/s、625 μs 时隙、79 RF 信道）见 `benchmark_v3/evidence/_bt_standard_hits.txt`。

5. 微波炉泄漏 50/60 Hz 调幅的**硬引用**。
6. VFD 载频范围与 IEC 61800-3 的对应条款。

## 2. 实现方案（生成器侧）

`benchmark_v3/simulation/em_signal_simulator_v3/emitters.py`：

1. 每个有时基的生成器加**物理速率参数**（单位 Hz），并从**窗长**推导事件数：
   `n_events = max(1, round(rate_hz * length / fs))`，事件起始相位按 rng 均匀分布
   （不是"每窗从头开始"，否则跨窗拼接会出现周期性伪影）。
2. 每类的速率/时长常量集中放在模块顶部的一张表（`TIMEBASE`），并在注释里写明依据与待核对状态，
   与本文档逐条对应。
3. 连续类不动（duty≈1 的类没有时基问题）。
4. 语音/视频类的"包结构"（LTE、UAV_video、TV）保持现状（它们本就是连续波形 + 帧结构近似）。

冒烟验收（零 API，已执行）：`diag/_probe_timebase_check.py` 逐类在 10 ms / 100 ms / 1 s 窗上核对
**放置事件率 = 物理率**与窗内必在；`diag/_probe_timebase_duty.py` 给出 duty 对照。
验收结论：**9 类事件率全部等于物理率（各窗一致）**；高频类（蓝牙/DECT/VFD/微波炉/电晕/焊机）duty 与窗长基本无关；
低频类（Zigbee 10/s、WiFi 9.8/s）在 10 ms 窗因「窗口选取为含事件」duty 被抬高（1/窗长），100 ms 与 1 s 一致——这是设计说明，不是缺陷。
证据：`evidence/_timebase_check.txt`（验收表）、`evidence/_timebase_duty_after.txt`（duty 对照，重写后）。

## 2b. 实施记录（2026-10-14：已落地）

`emitters.py` 顶部新增 `FS_HZ = 4e6` 与 `TIMEBASE` 表（每类：事件率 Hz、单事件时长 s、依据），
并提供 `_tb_dur(key)`、`tb_n_events(rng, length, key)` 两个 helper；9 类事件发生器改为速率驱动：

```
span = length / float(n)                       # 本类事件周期（样点）
d = min(max(int(dur_n * rng.uniform(lo, hi)), min_len), max(int(span), min_len))
pos = int(round(k * span + rng.random() * max(span - d, 0.0)))   # 相位在事件周期内随机，事件必落在窗内
```

| 类 | 物理率 | 单事件 | 放置事件（10 ms / 100 ms / 1 s） | duty（10 ms / 100 ms / 1 s） |
|---|---|---|---|---|
| Bluetooth_FHSS | 1600 /s | 625 µs 时隙 | 16 / 160 / 1600 | 0.771 / 0.749 / 0.747 |
| UAV_RC_hopping | 400 /s | 1.4 ms | 4 / 40 / 400 | 0.252 / 0.242 / 0.239 |
| Zigbee | 10 /s | 2.5 ms | 1 / 1 / 10 | 0.164 / 0.016 / 0.016 |
| WiFi_burst | 9.8 /s | 1.2 ms | 1 / 1 / 10 | 0.050 / 0.005 / 0.004 |
| DECT | 100 /s | 417 µs×1–2 时隙 | 1 / 10 / 100 | 0.061 / 0.060 / 0.062 |
| Welder | 100 /s | 8 ms（抖动 0.6–1.0） | 1 / 10 / 100 | 0.426 / 0.310 / 0.296 |
| Corona | 100 /s | 2 ms（抖动 0.3–1.0） | 1 / 10 / 100 | 0.097 / 0.067 / 0.062 |
| VFD_noise | 8000 /s | 30 µs（脉宽 5–15%） | 80 / 800 / 8000 | 0.072 / 0.067 / 0.053 |
| Microwave | 100 /s | 8 ms（抖动 0.5–1.0） | 1 / 10 / 100 | 0.379 / 0.386 / 0.317 |

（duty 是 `mean(|x| ≥ 0.2·max|x|)` 口径；事件包络实测值低于「事件率 × 事件时长」是正常的，见主文档 §1。）

**改写前后对照（10 ms 窗）**：

| 类 | 改写前 | 改写后 |
|---|---|---|
| Bluetooth_FHSS | 609 跳/10 ms（≈61 k 跳/s），驻留 6–15 µs | **16 跳/10 ms（1600 跳/s）**，驻留 437–625 µs |
| Zigbee | 每窗固定 7 包（与窗长无关） | 0.1 包/10 ms（窗选取后 1）、10 包/s |

| Welder | 583 突发/10 ms（≈58 k/s） | 1 事件/10 ms（**100 Hz 工频半周期**） |
| Corona | 94 突发/10 ms（≈9.4 k/s） | 1 组/10 ms（**100 Hz**） |
| Microwave | 2133 突发/10 ms（≈213 k/s） | 1 导通段/10 ms（**100 Hz 调幅**） |

---

**已知后果（2026-10-14 冒烟实测）**：`rad_cls/_smoke_gen16.py` 在 19 类上跑 `gen_wave16(length=4096)`（=1 ms）后，
**蓝牙 obw=0.026、遥控 obw=0.012 低于 `BW_RANGE=(0.06,0.28)` 下界**（改写前是非物理的 61 k 跳/s 才把带宽撑起来）。
原因：按物理时基，1 ms 窗内蓝牙只有 1–2 跳、10 ms 窗 16 跳——**跳频源在短窗内本来就不占满带宽**。
⇒ 这正是「长短窗是事件级题轴前提」的另一面：要么接受「10 ms 窗只能看到慢跳」（并把 OBW 合同按类/按窗注明），
要么把观测窗推到 ≥100 ms（代价见下节）。

## 3. 影响面（必须提前讲清）

- **所有档位数据作废**：D1–D4 与 d5–d12 的事件率全变 ⇒ GT 切片/gate 的既有数字（0.472/0.551/0.378 等）
  与新分数不可比；旧数据按既有规则归档到 `benchmark_v3/_pre_timebase_<日期>/`。
- **CNN 需要重训**：训练池 `data_gen16.gen_wave16` 走同一批生成器，波形统计会变。
- **评测口径不变**：七轴、门限、答案键字段都不动；变的只是"源在时间上的样子"。
- **长窗题与"事件级题轴"在此之后才立得住**。
